# 레거시 PHP 사이트 개인정보처리방침 점검하기

오래 운영한 PHP 사이트의 개인정보처리방침은 문구만 고치면 끝나는 작업처럼 보이기 쉽다. 하지만 실제 유지보수에서는 현재 서비스 동작과 정책 문구가 맞는지, 여러 화면에 중복된 내용이 없는지, 수정한 파일이 실제 사용자 화면에 연결되는지까지 함께 확인해야 한다.

이 글에서는 레거시 PHP 사이트에서 개인정보 관련 안내를 수정할 때 개발자가 확인할 항목을 정리한다. 법률 해석이 아니라 **코드와 화면의 일관성을 유지하는 개발 관점의 점검 방법**에 초점을 맞춘다.

## 먼저 정책이 노출되는 위치를 찾는다

레거시 사이트에서는 개인정보처리방침이 하나의 독립 페이지에만 존재하지 않을 수 있다.

예를 들어 다음 위치를 함께 확인한다.

```text
footer 링크
회원가입 동의 영역
문의·상담 폼
개인정보처리방침 페이지
공통 include 파일
모바일 전용 페이지
```

PC와 모바일 소스가 분리된 오래된 PHP 사이트라면 같은 문구가 여러 파일에 복사되어 있을 가능성도 있다.

문구를 수정하기 전에 파일 검색으로 관련 표현을 먼저 찾으면 일부 화면만 바뀌는 문제를 줄일 수 있다.

```bash
grep -R "개인정보" .
grep -R "쿠키" .
```

실제 프로젝트에서는 검색 범위를 소스 디렉터리로 제한하고 캐시, 로그, 업로드 디렉터리는 제외하는 편이 효율적이다.

## 정책 문구와 실제 기능을 대조한다

정책에는 현재 사이트가 실제로 사용하는 기능만 정확하게 설명되어야 한다.

개발자는 문구를 작성하는 역할과 별개로, 기술적으로 사실인지 확인할 수 있다.

### 쿠키 사용 여부

브라우저 개발자 도구의 Application 또는 Storage 영역에서 사이트가 생성하는 쿠키를 확인한다.

PHP 세션을 사용한다면 세션 쿠키가 생성될 수 있고, 분석 도구나 외부 서비스가 추가 쿠키를 사용할 수도 있다. 반대로 코드에서 더 이상 사용하지 않는 기능을 예전 정책 문구가 계속 설명하고 있을 수도 있다.

정책을 수정할 때는 다음을 대조한다.

```text
정책에 적힌 쿠키 용도
↕
실제 브라우저에서 생성되는 쿠키
↕
PHP 및 프런트엔드 코드의 사용처
```

쿠키 거부 방법을 안내한다면 특정 브라우저의 오래된 메뉴 이름을 고정해서 쓰기보다 현재 서비스 정책에 맞는 표현인지 별도로 검토한다.

## 외부 링크와 외부 서비스 경계를 구분한다

사이트에 외부 링크가 있다면 사용자가 다른 사이트로 이동한 이후의 처리 주체가 달라질 수 있다.

개발 측에서는 우선 링크가 실제로 어디로 연결되는지 확인한다.

```html
<a href="https://example.com/guide">안내 페이지</a>
```

특히 오래된 PHP 코드에서는 URL이 여러 include 파일이나 설정값에 흩어져 있을 수 있다. 화면에 표시되는 링크 텍스트만 보고 판단하지 말고 최종 `href` 값과 리다이렉트 여부를 확인한다.

정책에 외부 사이트 관련 안내가 있다면 현재 남아 있는 외부 링크와 불일치하지 않는지도 함께 점검한다.

## 문의 폼에서 실제 수집 항목을 확인한다

개인정보 관련 안내를 수정할 때 가장 놓치기 쉬운 부분이 문의·상담 폼이다.

화면에 다음과 같은 입력 항목이 있다고 가정한다.

```text
업체명
연락처
이메일
문의 내용
```

정책 문구만 확인하지 말고 HTML의 `input`, `textarea`와 서버의 PHP 처리 코드, DB 저장 컬럼을 함께 살펴본다.

```text
HTML form
  ↓
PHP request 처리
  ↓
DB 저장 또는 메일 발송
```

화면에서 삭제한 입력값을 서버 코드가 여전히 받거나, 반대로 새 입력값이 정책에 반영되지 않은 상태가 생길 수 있기 때문이다.

## 민원·문의 안내도 실제 연결 상태를 확인한다

정책 페이지에 문의 방법이 적혀 있어도 실제 링크가 깨져 있으면 사용자 입장에서는 기능하지 않는다.

개발자는 다음 정도를 확인할 수 있다.

- 문의 페이지 URL이 존재하는가
- 폼 제출이 정상적인 처리 경로로 연결되는가
- 오래된 이메일이나 담당자 정보가 코드에 하드코딩되어 있지 않은가
- PC와 모바일에서 같은 안내를 제공하는가

실제 이메일 주소나 담당자 정보는 코드 예제와 로그를 외부에 공유할 때 반드시 일반화한다.

## 공통 include로 중복을 줄인다

PC와 모바일, 여러 언어 페이지에 같은 정책 링크나 안내가 반복된다면 공통화할 수 있는지 검토한다.

```php
<?php include_once __DIR__ . '/includes/privacy_notice.php'; ?>
```

다만 레거시 프로젝트에서 무리하게 구조 전체를 바꾸는 것은 위험할 수 있다. 우선 수정 범위를 파악한 뒤 반복 변경으로 오류가 생기기 쉬운 부분부터 공통화하는 편이 안전하다.

상대 경로를 사용하는 include는 호출 위치에 따라 예상과 다른 파일을 찾을 수 있으므로 `__DIR__`를 기준으로 경로를 명확히 만드는 것도 도움이 된다.

## 수정 후에는 화면 기준으로 다시 확인한다

정책 파일을 수정했다면 소스만 확인하지 말고 실제 접근 경로에서 검증한다.

```text
1. PC 정책 페이지 확인
2. 모바일 정책 페이지 확인
3. footer 링크 확인
4. 문의·상담 폼의 동의 영역 확인
5. 외부 링크 확인
6. 브라우저 쿠키 확인
```

서버나 브라우저 캐시가 있는 사이트라면 변경된 파일이 실제 응답에 반영됐는지도 확인한다.

## 개인정보가 로그에 남지 않는지도 확인한다

문의 폼 오류를 추적하려고 request 전체를 로그로 출력하면 이메일, 전화번호, 문의 내용 같은 값이 그대로 남을 수 있다.

개발 로그가 필요하다면 상태와 오류 원인을 중심으로 남기고 불필요한 개인정보는 제외하거나 마스킹한다.

```text
좋지 않은 예: 전체 POST 데이터 출력
권장 방향: 처리 단계, 성공 여부, 내부 오류 코드 중심 기록
```

운영 로그의 보관 위치와 접근 권한도 함께 확인할 필요가 있다.

## 정리

레거시 PHP 사이트의 개인정보처리방침 수정은 텍스트 교체만으로 끝내기보다 실제 기능과 함께 확인해야 한다.

핵심 흐름은 다음과 같다.

```text
정책 노출 위치 검색
  ↓
실제 수집 항목·쿠키·외부 링크 대조
  ↓
PC·모바일 중복 확인
  ↓
문의 처리와 로그 점검
  ↓
실제 화면에서 최종 확인
```

개발자가 법률 판단을 대신할 수는 없지만, **사이트가 실제로 하는 일과 사용자에게 보여주는 안내가 기술적으로 어긋나지 않도록 만드는 것**은 개발 유지보수에서 중요한 역할이다.
