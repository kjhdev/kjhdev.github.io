매일 장이 끝난 뒤 시장 흐름을 확인하려면 여러 정보를 따로 찾아봐야 한다. KOSPI와 KOSDAQ이 얼마나 움직였는지, 거래가 집중된 종목은 무엇인지, 수급은 어떻게 변했는지, 시장에 영향을 준 주요 이슈는 무엇이었는지를 각각 확인해야 한다.

반복해서 확인하는 정보라면 직접 데이터를 수집하고 정리해 한 페이지에서 볼 수 있게 만들 수 있다고 생각했다. 여기서 **주식시장 데일리 브리핑 시스템** 프로젝트를 시작했다.

이 프로젝트의 목표는 단순히 주식 관련 글을 많이 작성하는 것이 아니다. 시장 데이터를 자동으로 수집하고, 검증하고, 저장한 뒤 필요한 정보만 정리해 매일 하나의 브리핑으로 만드는 것이다.

이번 글에서는 실제 구현 과정에 들어가기 전에 프로젝트를 시작한 이유와 현재 설계한 전체 구조를 정리한다.

## 기존 Office 블로그의 방향을 바꾸기로 했다

기존 `office.bubudev.com`은 Office 활용과 자동화 관련 글을 작성하는 블로그로 운영하고 있었다.

하지만 운영을 계속하면서 콘텐츠의 방향이 넓고, 장기적으로 어떤 내용을 지속해서 작성할 것인지가 명확하지 않다는 문제가 있었다. 자동으로 글을 생성하는 것만으로는 실제로 사용되는 서비스나 개발 프로젝트라는 느낌도 부족했다.

그래서 단순히 글을 작성하는 블로그가 아니라 **실제 데이터를 기반으로 매일 새로운 정보를 제공하는 사이트**로 방향을 변경했다.

주제로 선택한 것은 국내 주식시장이다.

목표는 다음 한 문장으로 정리할 수 있다.

> 하루 동안의 국내 주식시장 흐름을 한 페이지에서 빠르게 확인할 수 있는 브리핑을 매일 자동으로 만든다.

이 목표를 기준으로 필요한 데이터와 수집 방식, 저장 구조, 포스트 생성 방식까지 하나씩 설계하기 시작했다.

## 단순한 주식 블로그가 목표는 아니다

이 프로젝트에서 중요한 것은 시장에 대한 의견을 매일 직접 작성하는 것이 아니다.

사람이 매일 여러 사이트를 확인하고 숫자를 복사해 글을 작성하는 대신, 반복 가능한 부분을 시스템으로 만드는 것이 핵심이다.

현재 생각하고 있는 전체 흐름은 다음과 같다.

```text
주식시장 데이터
↓
Kiwoom REST API
↓
시장 데이터 수집기
↓
MySQL 저장
↓
브리핑 데이터 가공
↓
Markdown 포스트 생성
↓
Astro 정적 페이지 생성
↓
GitHub Actions 배포
↓
office.bubudev.com
```

사용자가 사이트에 접속할 때마다 주식 API를 호출하는 구조가 아니다. 장이 끝난 뒤 필요한 데이터를 한 번 수집하고, 그 결과를 정적인 콘텐츠로 만들어 배포하는 방식이다.

## 왜 정적 사이트 구조를 유지했을까

주식 데이터를 사용한다고 하면 실시간 백엔드 서버가 먼저 떠오른다. 하지만 이 프로젝트는 실시간 시세 서비스가 아니다.

목표는 하루 시장이 끝난 뒤 그날의 흐름을 정리한 브리핑을 제공하는 것이다. 따라서 사용자가 페이지를 열 때마다 데이터베이스를 조회하거나 외부 API를 호출할 필요가 없다.

```text
장 종료
↓
시장 데이터 수집
↓
브리핑 생성
↓
정적 HTML 생성
↓
배포
↓
사용자는 완성된 페이지 조회
```

이 구조에서는 웹사이트 자체를 기존 Astro 정적 사이트로 유지할 수 있다.

백엔드 역할은 웹 요청을 실시간으로 처리하는 것이 아니라 **데이터를 수집하고 콘텐츠를 생성하는 배치 프로그램**으로 한정한다. 사이트 구조가 단순해지고 외부 API 장애가 사용자 페이지 조회에 직접 영향을 주지 않는 장점도 있다.

## 데이터 수집기는 사이트와 분리한다

시장 데이터 수집에는 Kiwoom REST API를 사용하고 있다.

수집 프로그램은 블로그 프로젝트 안에서 모든 기능을 처리하지 않고 별도의 Docker 기반 Collector로 구성했다. 웹사이트는 생성된 결과를 보여주는 역할에 집중하고, 데이터 수집기는 서버에서 정해진 시간에 실행된다.

```text
[수집 영역]
Kiwoom REST API
→ Collector
→ MySQL

[게시 영역]
MySQL 데이터
→ 포스트 생성
→ Astro
→ GitHub
→ 배포
```

두 영역을 분리하면 수집 로직을 수정하더라도 사이트 자체를 크게 변경할 필요가 없다. 반대로 화면이나 포스트 레이아웃을 변경해도 API 수집 코드에는 영향을 주지 않는다.

## QuantPick과 데이터도 분리했다

별도로 개발 중인 QuantPick에서도 국내 주식 데이터를 수집하고 있다. 처음에는 이미 수집하고 있는 데이터를 Office에서 함께 사용하는 방법도 생각할 수 있었다.

하지만 두 프로젝트의 목적이 다르기 때문에 직접 의존하지 않도록 구성했다.

QuantPick은 개별 종목의 장기간 데이터를 수집하고 분석하기 위한 프로젝트다. Office는 하루 시장을 요약하는 데 필요한 데이터만 수집하면 된다.

데이터베이스도 이를 기준으로 분리했다.

```text
MySQL
├── quant   : QuantPick 데이터
└── market  : Office 시장 브리핑 데이터
```

Office는 `market` 스키마만 사용한다. 한 프로젝트의 수집 로직이나 테이블 변경이 다른 프로젝트에 직접 영향을 주지 않도록 하기 위한 선택이다.

## 데이터를 가져오는 것보다 먼저 검증한다

외부 API에서 응답이 왔다고 해서 바로 정상 데이터라고 판단하면 안 된다.

실제 수집기를 만들면서 먼저 넣은 것이 `preflight` 단계다. 전체 수집을 실행하기 전에 최소한의 API 호출로 기준 거래일, 주요 지수 값, 거래대금 데이터 등 핵심 응답이 정상인지 확인한다.

기본 흐름은 다음과 같다.

```text
API 요청
↓
응답 확인
↓
필수 데이터 검증
↓
DB 저장
↓
저장 결과 검증
```

데이터 기반 콘텐츠에서는 프로그램이 에러 없이 끝나는 것보다 **잘못된 값이 정상 데이터처럼 게시되지 않는 것**이 더 중요하다.

따라서 이 프로젝트에서도 수집 로직과 검증 로직을 함께 만들어가는 것을 기본 원칙으로 두었다.

## 매일 오후 11시에 수집한다

현재 시장 데이터 수집기는 서버의 Docker 환경에서 실행한다.

자동 실행은 `systemd timer`를 사용하고 있으며 매일 오후 11시에 동작하도록 설정했다. 장 종료 후 데이터를 정리해 수집하기에 충분한 시간을 두고, 이후 브리핑 생성 단계까지 연결하기 위한 시간이다.

```text
23:00
↓
systemd timer
↓
Docker Collector 실행
↓
시장 데이터 수집 및 검증
↓
MySQL 저장
```

`cron` 대신 `systemd timer`를 선택한 이유와 Docker 수집기를 배치 프로그램처럼 운영하는 방법은 이후 글에서 별도로 다룰 예정이다.

## 현재 사용하고 있는 구성

현재 프로젝트에서 사용하고 있는 주요 기술은 다음과 같다.

| 영역 | 구성 |
| --- | --- |
| 시장 데이터 | Kiwoom REST API |
| 데이터 수집 | Python Collector |
| 데이터베이스 | MySQL |
| 실행 환경 | Docker |
| 스케줄링 | systemd timer |
| 사이트 | Astro |
| 소스 관리 | GitHub |
| 배포 | GitHub Actions |
| 서비스 | office.bubudev.com |

각 기술 자체보다 이 요소들을 어떻게 연결해 반복 가능한 하나의 흐름으로 만드는지가 프로젝트의 핵심이다.

## 현재 어디까지 진행됐을까

이 프로젝트는 아직 진행 중이다.

현재까지는 시장 데이터 수집에 필요한 기본 구조를 만들고, API 사전 검증과 MySQL 저장 구조, Docker 실행 환경, 매일 오후 11시 자동 수집 스케줄까지 구성했다.

반면 수집된 데이터를 이용해 실제 브리핑을 생성하고 포스트 작성부터 배포까지 완전히 하나의 파이프라인으로 연결하는 작업은 계속 진행하고 있다.

현재 상태를 단순하게 나누면 다음과 같다.

```text
완료 또는 기본 구성 완료
- 시장 데이터 수집 구조
- API 사전 검증
- MySQL market 스키마
- Docker Collector
- 23:00 systemd timer

진행 중
- 브리핑용 데이터 가공
- Markdown 자동 생성
- 포스트 검증
- 수집부터 배포까지 전체 자동화
```

완성된 시스템을 나중에 한 번에 정리하기보다 실제로 만들어가는 과정에서 구조가 어떻게 바뀌고 어떤 문제가 발생했는지를 함께 기록할 예정이다.

## 다음 단계

다음으로 정해야 할 것은 **데일리 브리핑에 어떤 데이터를 넣을 것인가**이다.

데이터를 많이 수집한다고 좋은 브리핑이 되는 것은 아니다. 지수, 거래대금, 상승·하락 종목, 투자자 수급, 업종 흐름 등 여러 데이터 중 하루 시장을 빠르게 파악하는 데 필요한 항목을 먼저 선정해야 한다.

다음 글에서는 **「어떤 주식시장 데이터를 수집할 것인가」**를 주제로 브리핑에 필요한 데이터와 수집 기준을 정리한다.
