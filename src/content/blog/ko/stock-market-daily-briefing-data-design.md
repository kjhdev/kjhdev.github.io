[1화](/ko/posts/stock-market-daily-briefing-system-intro/)에서는 국내 주식시장 데이터를 수집해 매일 하나의 브리핑으로 만드는 전체 구조를 정리했다.

다음 문제는 단순했다.

**그래서 어떤 데이터를 수집해야 하는가?**

처음에는 주식 관련 데이터라면 많을수록 좋다고 생각하기 쉽다. 하지만 실제로 수집기를 만들기 시작하면 데이터가 하나 늘어날 때마다 API 호출, 저장 테이블, 단위 변환, 누락 검증, 게시 로직까지 함께 늘어난다.

이 프로젝트는 종목 분석 시스템이 아니라 **하루 시장의 흐름을 빠르게 이해하기 위한 데일리 브리핑**이다. 따라서 가능한 모든 데이터를 모으는 대신, 브리핑이 답해야 할 질문부터 정하고 그 질문에 필요한 데이터만 수집하기로 했다.

## 브리핑이 답해야 할 다섯 가지 질문

하루 시장을 정리할 때 우선 확인하고 싶은 것은 다음 다섯 가지였다.

1. 오늘 KOSPI와 KOSDAQ은 얼마나 움직였는가?
2. 지수만 오른 것인가, 실제로 많은 종목이 함께 올랐는가?
3. 개인·외국인·기관 중 누가 사고 누가 팔았는가?
4. 어떤 업종이 강했고 어떤 업종이 약했는가?
5. 거래는 어떤 종목에 집중됐는가?

이 다섯 질문을 기준으로 수집 범위를 나누니 필요한 데이터가 훨씬 명확해졌다.

```text
시장 방향        → KOSPI / KOSDAQ 지수
시장 확산 정도   → 상승 / 보합 / 하락 종목 수
수급             → 개인 / 외국인 / 기관 순매수
업종 흐름        → 업종별 등락률과 종목 분포
관심 집중 종목   → 거래대금 순위
```

현재 Office의 `market` 스키마도 이 구조를 기준으로 나뉘어 있다.

## 1. 가장 먼저 필요한 것은 KOSPI와 KOSDAQ 지수다

브리핑의 출발점은 시장 전체 방향이다.

KOSPI와 KOSDAQ의 종가와 등락률만 있어도 상승장인지 하락장인지 빠르게 알 수 있다. 하지만 실제 수집 데이터는 종가 하나만 저장하지 않는다.

현재 지수 데이터에는 다음 항목을 저장한다.

- 시가
- 고가
- 저가
- 종가
- 전일 대비 변화값
- 등락률
- 거래량
- 거래대금

이를 `market_index_daily` 테이블에 거래일과 시장별로 저장한다.

종가와 등락률은 브리핑의 대표 숫자로 사용하고, 시가·고가·저가는 장중 흐름을 설명할 때 사용한다. 예를 들어 같은 `+1%` 상승이라도 장 초반부터 꾸준히 오른 날과 장중 크게 밀렸다가 반등한 날은 전혀 다른 하루다.

따라서 지수 데이터는 단순히 "올랐다 / 내렸다"를 표시하기 위한 값이 아니라 하루 시장 흐름의 기준점 역할을 한다.

## 2. 지수만으로는 부족해서 시장 폭을 추가했다

지수가 상승했다고 해서 모든 종목이 오른 것은 아니다.

시가총액 비중이 큰 몇 개 종목이 강하게 오르면 상당수 종목이 하락해도 지수는 상승할 수 있다. 반대로 지수가 크게 오르지 않아도 시장 전체에서는 상승 종목이 훨씬 많을 수 있다.

그래서 두 번째로 추가한 것이 **시장 폭(Market Breadth)** 데이터다.

현재 `market_breadth_daily`에는 시장별로 다음 값을 저장한다.

- 상한가 종목 수
- 상승 종목 수
- 보합 종목 수
- 하락 종목 수
- 하한가 종목 수
- 거래량
- 거래대금

예를 들어 KOSDAQ이 크게 상승한 날 상승 종목도 압도적으로 많다면 "일부 종목만 끌어올린 지수 상승"보다는 "시장 전반으로 상승이 확산된 날"이라고 설명할 수 있다.

반대로 지수는 상승했는데 하락 종목이 더 많다면 대형주 중심의 상승인지 확인할 필요가 있다.

브리핑에서 체감 시장을 설명하려면 지수와 시장 폭을 함께 보는 편이 훨씬 유용했다.

## 3. 누가 사고팔았는지 보기 위해 투자자 수급을 수집한다

시장 방향 다음으로 자주 확인하는 것은 투자자별 수급이다.

현재 `market_investor_daily`에는 KOSPI와 KOSDAQ 각각에 대해 다음 세 주체의 순매수 금액을 저장한다.

- 개인
- 외국인
- 기관

이 데이터가 있으면 단순히 "KOSPI가 상승했다"에서 끝나지 않고 다음처럼 한 단계 더 설명할 수 있다.

```text
KOSPI 상승
+
외국인 순매수
+
기관 순매수
+
개인 순매도
```

지수 움직임과 매매 주체의 방향을 함께 보면 그날 상승이나 하락을 누가 주도했는지 파악하기 쉬워진다.

업종별 수급도 별도의 `market_sector_investor_daily`에 저장할 수 있도록 분리했다. 전체 시장 수급과 업종별 수급을 같은 테이블에 섞지 않고 목적에 따라 나눈 것이다.

## 4. 업종 데이터를 넣어 상승의 위치를 확인한다

시장 전체가 올랐다는 정보만으로는 실제 돈이 어디로 이동했는지 알기 어렵다.

그래서 `market_sector_daily`에는 업종별로 다음 데이터를 저장한다.

- 업종 지수 현재값
- 등락값과 등락률
- 거래량과 거래대금
- 상승·보합·하락 종목 수
- 상한가·하한가 종목 수
- 상장 종목 수

브리핑에서는 이 데이터를 이용해 강세 업종과 상대적으로 약한 업종을 구분할 수 있다.

여기서 중요한 것은 단순히 등락률 1위 업종 하나만 보여주는 것이 아니다. 업종 지수가 올랐을 때 실제로 그 업종에 포함된 여러 종목이 함께 상승했는지도 확인할 수 있어야 한다.

즉 업종에서도 **등락률과 시장 폭을 같이 본다**.

## 5. 개별 종목은 거래대금 순위부터 시작했다

데일리 브리핑에 개별 종목을 넣을 때 가장 고민했던 부분은 "어떤 종목을 보여줄 것인가"였다.

등락률 상위 종목만 나열하면 변동성이 큰 소형주가 계속 등장할 수 있다. 시가총액 상위 종목만 보면 실제로 그날 시장에서 관심이 집중된 종목을 놓칠 수 있다.

첫 기준으로 선택한 것은 **거래대금**이다.

`market_ranking_daily`에는 순위 유형, 순위, 종목코드, 종목명, 현재가, 등락률, 기준값 등을 저장하도록 구성했다.

현재 브리핑에서는 거래대금 상위 종목을 이용해 그날 실제 거래가 집중된 종목을 확인한다.

거래대금이 높다는 이유만으로 좋은 종목이라는 뜻은 아니다. 이 데이터의 목적은 추천이 아니라 **그날 시장의 관심이 어디에 모였는지 확인하는 것**이다.

이 기준을 명확히 해두면 데일리 브리핑이 종목 추천 글로 변하는 것도 막을 수 있다.

## 수집 테이블과 게시용 요약 테이블을 분리했다

수집한 데이터를 바로 Markdown에 넣는 구조로 만들 수도 있다. 하지만 그렇게 하면 포스트 생성 코드가 여러 원천 테이블의 구조를 모두 알아야 한다.

현재는 원천 데이터를 의미별로 나눈 뒤 게시 단계에서 자주 사용하는 값을 `daily_summary`로 한 번 더 정리하는 구조를 사용한다.

| 역할 | 테이블 | 주요 데이터 |
| --- | --- | --- |
| 시장 방향 | `market_index_daily` | KOSPI·KOSDAQ 지수, 거래량, 거래대금 |
| 시장 체감 | `market_breadth_daily` | 상승·보합·하락 종목 수 |
| 업종 흐름 | `market_sector_daily` | 업종별 등락률과 종목 분포 |
| 투자자 수급 | `market_investor_daily` | 개인·외국인·기관 순매수 |
| 업종 수급 | `market_sector_investor_daily` | 업종별 투자자 순매수 |
| 종목 관심도 | `market_ranking_daily` | 거래대금 등 순위 데이터 |
| 게시용 요약 | `daily_summary` | 브리핑에 자주 쓰는 핵심값 |

이렇게 분리하면 수집기와 포스트 생성기가 직접 강하게 결합되지 않는다.

예를 들어 지수 API의 응답 필드가 바뀌더라도 수집 단계에서 정규화한 뒤 `daily_summary`의 형태만 유지하면 게시 로직에 미치는 영향을 줄일 수 있다.

## 날짜와 단위도 데이터의 일부로 취급했다

주식 데이터를 저장할 때 값 자체만 맞는다고 끝나는 것은 아니다.

특히 자동 수집에서는 다음 문제가 자주 생길 수 있다.

- 요청한 날짜와 실제 응답 거래일이 다름
- 휴장일 때문에 직전 거래일 데이터가 반환됨
- 거래대금 단위가 API마다 다름
- 같은 숫자라도 시장별 기준이 다름
- 일부 데이터만 최신 거래일이고 나머지는 이전 거래일임

그래서 테이블에는 `trade_date`를 명확히 저장하고, 금액 데이터에는 `trading_value_unit`, `amount_unit`처럼 단위를 함께 기록했다. 어떤 API에서 가져온 값인지 확인할 수 있도록 `source_api`도 남긴다.

수집 실행 자체도 `collection_run`에 시작 시각, 종료 시각, 요청 기준일, 실제 거래일, 요청 횟수와 상태를 기록한다.

숫자를 모으는 것뿐 아니라 **그 숫자가 언제, 어떤 기준과 단위로 수집됐는지 추적할 수 있게 만드는 것**도 데이터 설계의 일부라고 판단했다.

## 처음부터 모든 주식 데이터를 모으지 않은 이유

Office와 별도로 QuantPick에서는 개별 종목의 장기간 가격, 수급, 프로그램 매매, 공매도, 신용, 대차 같은 데이터를 더 넓게 수집하고 있다.

하지만 Office에서 같은 데이터를 다시 모두 수집할 필요는 없다.

두 프로젝트의 질문이 다르기 때문이다.

```text
QuantPick
→ 어떤 종목의 단기 수익 가능성이 높은가?

Office Market Briefing
→ 오늘 시장에서 어떤 일이 있었는가?
```

질문이 다르면 필요한 데이터도 달라진다.

Office는 하루 시장을 설명하는 데 직접 사용하지 않는 장기 개별 종목 데이터는 초기 범위에서 제외했다. 실시간 체결, 호가 데이터처럼 데일리 브리핑 목적에 비해 수집량이 큰 데이터도 우선순위에서 뺐다.

이렇게 범위를 줄이면 API 호출 수와 저장량을 줄이는 효과도 있지만, 더 중요한 장점은 **검증해야 할 데이터의 범위가 명확해진다는 것**이다.

## 데이터 선정 기준을 네 가지로 정리했다

현재는 새로운 데이터를 추가할 때 다음 기준을 먼저 확인한다.

### 1. 브리핑에서 실제로 사용할 수 있는가

수집할 수 있다는 이유만으로 추가하지 않는다. 독자가 하루 시장을 이해하는 데 직접 도움이 되는지를 먼저 본다.

### 2. 매일 같은 기준으로 반복 수집할 수 있는가

자동화에서는 한 번 가져오는 것보다 매일 안정적으로 같은 형태로 가져올 수 있는지가 중요하다.

### 3. 수집 결과를 검증할 수 있는가

거래일, 건수, 값의 범위, 단위 등을 확인할 수 있어야 한다. 정상 여부를 판단하기 어려운 데이터는 자동 게시에도 사용하기 어렵다.

### 4. API 호출 비용에 비해 가치가 있는가

외부 API에는 호출 제한이 있다. 한 번의 브리핑을 위해 필요 이상으로 많은 요청을 사용하는 구조는 장기적으로 안정적이지 않다.

결국 "있으면 좋은 데이터"와 "브리핑에 반드시 필요한 데이터"를 구분하는 것이 중요했다.

## 현재 브리핑 데이터 흐름

현재 데이터 흐름을 단순화하면 다음과 같다.

```text
KOSPI / KOSDAQ 지수
시장 폭
투자자 수급
업종
거래대금 순위
        ↓
MySQL market 스키마
        ↓
daily_summary 및 브리핑용 가공
        ↓
Markdown 포스트
        ↓
Astro 빌드 및 배포
```

1화에서 전체 시스템 구조를 정했다면, 이번 단계에서는 그 안으로 들어올 데이터의 범위를 정한 셈이다.

이 과정을 거치고 나니 수집기의 목적도 더 명확해졌다. 수집기의 목표는 가능한 많은 주식 데이터를 저장하는 것이 아니라 **매일 같은 기준으로 신뢰할 수 있는 시장 요약 데이터를 만드는 것**이다.

## 다음 단계

수집할 데이터를 정했다고 바로 전체 수집을 실행할 수 있는 것은 아니다.

실제로 자동 수집에서 더 위험한 것은 API 요청이 실패하는 경우보다, **잘못된 거래일이나 비정상적인 값이 정상 데이터처럼 저장되는 경우**다.

그래서 전체 수집 전에 소량의 API 호출로 거래일과 핵심 데이터를 먼저 검사하는 `preflight` 단계를 만들었다.

다음 글에서는 **「전체 수집 전에 왜 preflight 검증을 두었는가」**를 주제로, 데이터 수집 전에 어떤 값을 확인하고 잘못된 데이터를 어떻게 차단하는지 정리할 예정이다.
