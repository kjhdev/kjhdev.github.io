다국어 기술 블로그에서 본문만 번역하고 이미지 속 텍스트는 한 언어로 남겨두면 글의 완성도가 떨어진다.

특히 흐름도나 설정 설명처럼 이미지 자체에 텍스트가 들어가면 한국어 글과 영어 글에 각각 맞는 이미지를 제공하는 편이 자연스럽다. 정적 사이트에서는 이미지 파일 하나가 잘못되어도 빌드 이후에야 깨진 참조를 발견할 수 있으므로, 생성 단계에서 구조와 참조를 함께 검증하는 것이 중요하다.

이 글에서는 Astro 기반 다국어 블로그에서 SVG를 언어별로 관리하고 배포 전에 확인할 항목을 정리한다.

## 언어별 Markdown과 이미지를 함께 분리한다

콘텐츠가 다음처럼 언어별 디렉터리로 나뉘어 있다고 가정한다.

```text
src/content/blog/
├── ko/
│   └── example.md
└── en/
    └── example.md
```

이미지에 텍스트가 없다면 두 글이 같은 이미지를 공유해도 된다.

반대로 이미지에 제목, 단계명, 설명 문구가 포함된다면 파일도 언어별로 나누는 편이 명확하다.

```text
public/images/posts/example/
├── workflow-ko.svg
└── workflow-en.svg
```

파일명에 언어를 포함하면 Markdown을 검토할 때 잘못된 언어의 이미지를 연결했는지 빠르게 확인할 수 있다.

## Markdown 참조와 실제 파일을 함께 확인한다

한국어 글에서는 한국어 이미지를 참조한다.

```md
![배포 전 콘텐츠 검증 흐름](/images/posts/example/workflow-ko.svg)
```

영어 글에서는 대응하는 영어 이미지를 사용한다.

```md
![Content validation flow before deployment](/images/posts/example/workflow-en.svg)
```

여기서 중요한 것은 Markdown 문자열만 확인하지 않는 것이다. 참조된 경로에 실제 파일이 존재하는지도 함께 검사해야 한다.

정적 사이트에서는 경로의 대소문자 차이도 배포 환경에 따라 문제가 될 수 있으므로 파일명과 참조 경로를 정확히 맞춘다.

## SVG는 텍스트 파일이라고 무조건 안전하지 않다

SVG는 XML 기반 텍스트 형식이라 Git에서 다루기 편하지만, 내용 자체도 검증해야 한다.

최소한 다음 항목을 확인한다.

### svg 루트와 닫힘 태그

파일이 정상적인 SVG 문서인지 확인한다.

```xml
<svg viewBox="0 0 1200 630"
     xmlns="http://www.w3.org/2000/svg">
    ...
</svg>
```

잘린 파일이나 생성 도중 실패한 파일은 시작 태그만 있고 닫힘 태그가 없을 수 있다.

### 유효한 크기

`viewBox` 또는 `width`와 `height`가 유효해야 한다.

```xml
viewBox="0 0 1200 630"
```

너비나 높이가 0인 SVG는 파일 자체는 존재해도 화면에서 정상적으로 보이지 않는다.

### script와 외부 자산

블로그용 정적 이미지라면 불필요한 `<script>`를 넣지 않는 편이 안전하다.

외부 폰트, 외부 이미지 URL처럼 네트워크에 의존하는 자산도 피하면 배포 환경이나 외부 서비스 상태에 따른 이미지 깨짐을 줄일 수 있다.

## 바이너리 이미지는 SVG와 다르게 다룬다

PNG, JPEG, WebP는 SVG와 달리 바이너리 파일이다.

GitHub API나 자동화 코드에서 UTF-8 텍스트 파일을 만드는 방식으로 바이너리를 생성하면 파일이 손상될 수 있다.

따라서 자동화 과정에서는 형식에 따라 처리 방식을 구분해야 한다.

```text
SVG
→ UTF-8 텍스트로 생성 가능
→ XML 구조 검증

PNG / JPEG / WebP
→ 정상적인 이미지 생성 도구 사용
→ 실제 이미지 디코딩 검증
```

확장자만 `.png`라고 해서 정상 PNG가 되는 것은 아니다.

## alt 텍스트도 언어별로 작성한다

이미지 파일만 분리하고 alt 텍스트를 그대로 복사하면 다국어 페이지의 접근성과 문맥이 어색해진다.

alt 텍스트는 이미지에 보이는 모든 글자를 반복하기보다 이미지가 전달하는 핵심 의미를 해당 언어로 설명한다.

```md
![한국어 글 작성부터 이미지 검증까지의 흐름](...)
```

영어 글에서는 같은 의미를 자연스러운 영어로 작성한다.

## 자동화에서는 커밋 전에 검증한다

포스트 자동 생성 과정이라면 커밋 이후보다 커밋 전에 오류를 잡는 편이 낫다.

검증 순서는 단순하게 유지할 수 있다.

```text
Markdown 생성
→ 이미지 생성
→ Markdown 이미지 경로 추출
→ 실제 파일 존재 확인
→ SVG 구조 또는 바이너리 디코딩 확인
→ 사이트 빌드
→ 커밋
```

Astro 프로젝트에 `build` 스크립트가 있다면 마지막 단계에서 실제 콘텐츠 파싱과 정적 페이지 생성을 확인할 수 있다.

```bash
npm run build
```

빌드 성공만으로 이미지 내용까지 모두 보장되는 것은 아니므로 파일 존재와 이미지 자체 검증은 별도로 수행한다.

## 한국어와 영어 파일이 뒤바뀌는 것도 검사한다

자동 생성에서는 같은 slug의 한국어·영어 Markdown을 동시에 만들기 때문에 파일 복사 과정의 실수도 고려해야 한다.

다음 항목을 확인하면 단순한 언어 뒤바뀜을 잡는 데 도움이 된다.

- 한국어 파일의 `lang`이 `ko`인지 확인
- 영어 파일의 `lang`이 `en`인지 확인
- 두 Markdown의 내용이 동일하지 않은지 확인
- 한국어 글이 `-ko.svg`를 참조하는지 확인
- 영어 글이 `-en.svg`를 참조하는지 확인

본문의 명령어와 기술적 의미는 같아야 하지만 두 언어 파일 자체가 동일한 내용이어서는 안 된다.

## 정리

Astro 다국어 블로그에서 이미지 자동화는 이미지를 만드는 것으로 끝나지 않는다.

텍스트가 들어간 이미지는 언어별로 분리하고, Markdown 경로와 실제 파일을 함께 확인해야 한다. SVG는 루트 태그, 크기, 스크립트, 외부 자산을 검사하고 PNG·JPEG·WebP는 실제 바이너리 이미지로 정상 생성됐는지 확인한다.

마지막으로 Astro 빌드까지 통과시킨 뒤 커밋하면 깨진 이미지나 잘못된 언어 파일이 배포되는 가능성을 줄일 수 있다.
