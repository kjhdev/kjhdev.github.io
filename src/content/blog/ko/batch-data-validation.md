대량 API 수집기를 만들면서 가장 크게 바뀐 생각은 **수집기가 끝났다는 것과 데이터가 정상이라는 것은 전혀 다른 문제**라는 점이었다.

실제 작업 대상은 KOSPI·KOSDAQ 보통주 2,555개였다. 2년치 일봉을 적재했을 때 가격 데이터는 160만 건을 넘었다. 이 정도가 되면 화면에서 몇 종목을 조회하거나 전체 `COUNT(*)`만 확인해서는 누락을 찾기 어렵다.

초기에는 "에러 없이 종료 + row 수 증가"를 성공 기준으로 보기 쉬웠다. 하지만 특정 종목만 통째로 빠져도 전체 건수는 충분히 커 보였다. 이후 수집과 검증을 분리하고, 검증을 통과해야 초기화가 성공하도록 구조를 바꿨다.

## 실제로 필요했던 검증 단계

```text
API 수집
↓
MySQL 적재
↓
전체 건수 확인
↓
2555개 종목 커버리지 확인
↓
종목별 최소/최대 날짜 확인
↓
중복·값 정합성 확인
↓
허용 예외 분리
↓
PASS / WARNING / FAIL
```

### 1. 전체 건수는 시작점일 뿐

```sql
SELECT COUNT(*) FROM stock_price_daily;
```

전체 건수가 많아도 특정 종목이 0건일 수 있다. 그래서 마스터와 실제 데이터를 비교했다.

```sql
SELECT m.stock_code
FROM stock_master m
LEFT JOIN stock_price_daily d ON d.stock_code = m.stock_code
GROUP BY m.stock_code
HAVING COUNT(d.stock_code) = 0;
```

여기서 핵심 지표는 `1,600,000건 이상` 같은 숫자가 아니라 **2,555개 중 몇 종목이 정상적으로 포함됐는가**였다.

### 2. 기간도 종목별로 확인

```sql
SELECT stock_code,
       COUNT(*) AS cnt,
       MIN(trade_date) AS min_date,
       MAX(trade_date) AS max_date
FROM stock_price_daily
GROUP BY stock_code;
```

신규 상장 종목은 2년치 데이터가 존재할 수 없기 때문에 단순히 row 수가 적다는 이유로 실패시키지 않았다. 마스터 정보와 데이터 시작 시점을 함께 봐야 했다.

### 3. 0건을 무조건 실패시키지 않는다

실제 수집에서는 관리종목처럼 원천 API 자체에 데이터가 없는 경우도 있었다. 이를 모두 실패로 처리하면 정상적인 원천 특성이 매번 장애처럼 보인다.

그래서 결과를 세 단계로 나눴다.

```text
PASS    기대 데이터 존재 및 정합성 정상
WARNING 원천 데이터 부재 등 설명 가능한 예외
FAIL    실제 누락, 중복, 값 오류
```

중요한 점은 WARNING을 단순 무시 목록으로 만들지 않는 것이다. 종목 코드와 상태, 허용 이유를 로그에 남겨 나중에 예외가 늘어났는지 확인할 수 있게 했다.

## 투자자 데이터에서 발견한 '정상적인 잔차'

투자자 수급 데이터는 여러 주체의 값을 합산해 전체와 비교했다. 수량 합계는 검증 규칙으로 사용하기 좋았지만 금액 데이터에서는 원천의 단위·집계 특성 때문에 잔차가 대량으로 나타났다.

처음부터 `합계가 1이라도 다르면 FAIL`로 만들었다면 정상 데이터를 계속 실패로 판단했을 것이다.

그래서 실제 원천 데이터를 확인한 뒤:

- 수량 합계 이상 → 실패 후보
- 금액 잔차 → 건수를 기록하는 정보성 경고

처럼 규칙을 분리했다. **검증 규칙은 데이터의 실제 특성을 확인한 뒤 정해야 한다**는 점을 여기서 배웠다.

## 재실행해도 결과가 망가지지 않아야 한다

수백만 건 초기화는 서버 재부팅이나 API 제한으로 중간에 멈출 수 있다. 처음부터 다시 실행할 때 중복 데이터가 쌓이면 복구가 더 어려워진다.

그래서 종목·거래일처럼 업무적으로 유일한 키에 UNIQUE 제약을 두고 재실행 가능한 저장 방식을 사용했다.

```sql
UNIQUE KEY uk_stock_date (stock_code, trade_date)
```

검증기에서도 중복을 다시 확인한다.

```sql
SELECT stock_code, trade_date, COUNT(*)
FROM stock_price_daily
GROUP BY stock_code, trade_date
HAVING COUNT(*) > 1;
```

## 로그는 '성공'보다 근거를 남긴다

최종 로그에는 최소한 다음 정보가 있어야 했다.

```text
전체 행 수
마스터 대비 종목 커버리지
종목별 기간 이상 여부
원천 데이터 없음 허용 대상
정합성 경고 건수
중복 건수
최종 PASS / FAIL
```

문제가 생겼을 때 `성공` 한 줄보다 이 요약값이 훨씬 유용했다.

## 검증 실패를 프로세스 실패로 전달한다

Python 검증기는 오류가 있으면 종료코드 `1`을 반환하게 했다.

```python
if errors:
    raise SystemExit(1)
raise SystemExit(0)
```

쉘에서는 `set -e`와 결합해 검증 실패 후 다음 데이터셋으로 넘어가지 않게 했다.

```bash
set -e
python collect.py
python validate_raw_data.py --dataset price --history-years 2
```

## 초기 적재와 일일 수집에 같은 기준을 쓴다

2년치 초기 적재와 하루치 증분 수집은 데이터 양만 다를 뿐 핵심 품질 기준은 같다. 검증기를 데이터셋별로 재사용하도록 만들면 일일 자동 수집에서도 동일한 기준을 적용할 수 있다.

이 작업에서 가장 중요한 변화는 **"수집 완료"의 정의를 바꾼 것**이었다. API 호출이 끝난 시점이 아니라 마스터 커버리지, 기간, 중복, 정합성, 허용 예외까지 검증된 시점을 완료로 봐야 했다.

대량 데이터 수집에서는 더 많은 데이터를 빨리 넣는 것보다, 나중에 그 데이터를 믿고 사용할 수 있다는 근거를 만드는 것이 먼저다.
