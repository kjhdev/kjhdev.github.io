# 대용량 배치 수집 후 데이터 검증 설계하기

API에서 수십만~수백만 건을 MySQL에 적재하면 `INSERT`가 끝났다는 사실만으로 수집 성공을 판단하기 어렵다.

실제 배치에서는 일부 대상만 누락되거나, 특정 기간이 비거나, 원천 데이터가 없는 대상을 오류로 오인하는 문제가 더 위험하다. 이 글에서는 대량 수집 후 별도 검증 단계에서 확인할 항목을 정리한다.

## 수집과 검증을 분리한다

수집기가 데이터를 저장하면서 모든 검증까지 담당하면 코드가 복잡해진다. 수집 완료 후 별도 검증 프로그램을 실행하면 역할이 명확해진다.

```text
수집 실행
  ↓
DB 적재
  ↓
데이터셋별 검증
  ↓
정상 / 경고 / 실패 판정
```

수집기는 API 호출과 저장에 집중하고, 검증기는 이미 저장된 결과가 기대 조건을 만족하는지 확인한다.

## 전체 건수는 시작점일 뿐이다

가장 먼저 전체 건수를 확인할 수 있다.

```sql
SELECT COUNT(*)
FROM stock_data_daily;
```

하지만 예상보다 많은 건수가 있다는 사실만으로 완전성을 증명할 수는 없다. 일부 대상에 데이터가 집중되고 다른 대상이 통째로 빠질 수도 있기 때문이다.

따라서 전체 건수 다음에는 대상별 분포를 확인해야 한다.

```sql
SELECT item_code,
       COUNT(*) AS row_count,
       MIN(trade_date) AS min_date,
       MAX(trade_date) AS max_date
FROM stock_data_daily
GROUP BY item_code;
```

## 대상별 커버리지를 검증한다

마스터 테이블에 활성 대상이 있다면 수집 테이블과 비교해 누락 대상을 찾는다.

```sql
SELECT m.item_code
FROM item_master m
LEFT JOIN stock_data_daily d
    ON d.item_code = m.item_code
WHERE m.active = 1
GROUP BY m.item_code
HAVING COUNT(d.item_code) = 0;
```

핵심은 단순히 전체 row 수가 아니라 **수집 대상 각각에 필요한 데이터가 존재하는지** 확인하는 것이다.

기간 데이터라면 최소일과 최대일도 함께 검사한다. 신규 대상처럼 전체 이력이 존재할 수 없는 경우에는 상장일 또는 데이터 시작일 같은 기준을 별도로 적용한다.

## 원천 데이터 없음과 수집 실패를 구분한다

모든 `0건`을 실패로 처리하면 정상적인 예외가 계속 오류로 보고된다.

예를 들어 거래정지, 관리 상태, 신규 등록 등 원천 API 자체에 데이터가 없는 경우가 있을 수 있다. 검증기는 이를 최소 세 단계로 구분하는 편이 좋다.

```text
PASS    기대 조건 충족
WARNING 원천 특성상 허용 가능한 예외
FAIL    실제 누락 또는 정합성 오류
```

허용 예외에는 반드시 이유를 남긴다. 단순히 오류를 무시하도록 만들면 실제 장애도 함께 가려질 수 있다.

## 데이터 자체의 규칙을 검증한다

커버리지 이후에는 컬럼 간 관계를 검사한다.

예를 들어 여러 세부 값의 합이 전체 값과 일치해야 하는 데이터라면 SQL이나 Python에서 합계를 비교할 수 있다.

```text
세부 값 합계 == 전체 값
```

다만 금액 단위 변환, 반올림, 원천 API의 집계 기준 때문에 작은 잔차가 발생할 수 있다. 이 경우 무조건 실패시키기보다 허용 오차를 명시하고 정보성 경고로 분리한다.

중요한 것은 실제 데이터 특성을 확인한 뒤 허용 기준을 코드에 남기는 것이다.

## 재실행 안전성도 검증 대상이다

배치가 실패해 다시 실행될 수 있다면 같은 날짜와 같은 대상의 데이터가 중복되지 않아야 한다.

가능하면 DB에서 자연키 또는 업무키에 UNIQUE 제약을 둔다.

```sql
UNIQUE KEY uk_item_date (item_code, trade_date)
```

그리고 수집기는 `INSERT ... ON DUPLICATE KEY UPDATE`처럼 프로젝트 정책에 맞는 재실행 방식을 사용한다.

검증 단계에서도 중복을 확인한다.

```sql
SELECT item_code, trade_date, COUNT(*)
FROM stock_data_daily
GROUP BY item_code, trade_date
HAVING COUNT(*) > 1;
```

## 검증 로그는 사람이 판단할 수 있게 만든다

`검증 성공` 한 줄만 출력하면 나중에 문제가 생겼을 때 근거를 찾기 어렵다.

다음 정보를 함께 남기면 좋다.

```text
전체 건수
대상별 커버리지 결과
최소/최대 날짜
허용된 원천 데이터 없음 대상
정합성 경고 건수
중복 건수
최종 PASS / FAIL
```

대량 데이터에서는 모든 row를 로그로 출력할 필요가 없다. 요약 건수와 문제가 있는 대상만 출력하는 편이 운영하기 쉽다.

## 검증 실패 시 다음 배치로 넘어가지 않는다

검증 스크립트는 사람이 읽는 로그뿐 아니라 프로세스 종료 코드도 명확히 반환하는 것이 좋다.

```python
if errors:
    raise SystemExit(1)

raise SystemExit(0)
```

그러면 쉘 스크립트나 CI에서 검증 실패를 감지해 후속 단계를 중단할 수 있다.

```bash
python collect.py
python validate_data.py
```

`set -e`를 사용하는 배치라면 검증기의 비정상 종료가 다음 단계 실행을 막는다.

## 초기 적재와 일일 배치에 같은 기준을 재사용한다

초기 2년치 적재와 매일 한 번 실행하는 증분 수집은 데이터 양이 다르지만 핵심 검증 규칙은 공유할 수 있다.

검증기에 데이터셋과 기간을 인자로 전달하면 별도 프로그램을 계속 만들 필요가 없다.

```bash
python validate_data.py --dataset price --history-years 2
python validate_data.py --dataset investor --history-years 2
```

일일 배치에서는 검사 기간만 좁혀 동일한 규칙을 재사용할 수 있다.

## 마무리

대용량 데이터 수집의 완료 조건은 API 호출이 끝났거나 DB row 수가 증가한 시점이 아니다.

전체 건수, 대상별 커버리지, 기간, 중복, 컬럼 간 정합성, 원천 데이터 예외를 함께 확인해야 실제 분석에 사용할 수 있는 데이터인지 판단할 수 있다.

수집과 검증을 분리하고 검증 실패가 후속 단계로 전파되도록 구성하면 초기 대량 적재뿐 아니라 반복되는 일일 배치에서도 같은 기준을 유지할 수 있다.
