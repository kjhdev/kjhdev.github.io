[2화](/ko/posts/stock-market-daily-briefing-data-design/)에서는 데일리 브리핑에 어떤 데이터를 수집할 것인지 정리했다.

지수, 시장 폭, 투자자 수급, 업종, 거래대금 순위까지 수집 범위를 정하고 나면 다음 단계는 실제 API를 호출해 데이터를 저장하는 것이다.

하지만 자동 수집기를 만들면서 더 중요하다고 판단한 문제가 하나 있었다.

**API 호출에 성공했다는 사실과 정상 데이터를 받았다는 사실은 같지 않다.**

요청 자체가 실패하면 프로그램은 에러를 내고 멈춘다. 오히려 더 위험한 경우는 요청은 성공했는데 거래일이 예상과 다르거나, 핵심 목록이 비어 있거나, 일부 값이 비정상인 상태로 다음 단계까지 진행되는 것이다.

그래서 Office 시장 수집기에는 전체 수집을 시작하기 전에 최소한의 API 호출만 수행하는 `preflight` 단계를 별도로 두었다.

## preflight는 전체 수집 전에 통과해야 하는 작은 관문이다

이 프로젝트에서 `preflight`의 목적은 모든 데이터를 미리 검증하는 것이 아니다.

전체 수집을 실행해도 되는 기본 상태인지 빠르게 확인하는 것이 목적이다.

현재 흐름을 단순화하면 다음과 같다.

```text
preflight 실행
↓
API 인증 확인
↓
KOSPI 지수 조회
↓
실제 반환 거래일과 핵심 지수값 확인
↓
거래대금 상위 목록 조회
↓
응답 목록 존재 여부 확인
↓
현재 API 요청 수 확인
↓
정상일 때만 전체 수집 진행
```

즉, 수십 개의 데이터를 저장한 뒤 잘못됐다는 사실을 발견하는 대신 가장 대표적인 API 몇 개를 먼저 호출해 수집 환경 자체가 정상인지 확인한다.

## 왜 전체 수집부터 바로 실행하지 않았을까

처음 구현할 때는 전체 수집 프로그램 하나만 있어도 충분해 보인다.

```text
API 호출
→ 모든 데이터 수집
→ DB 저장
→ 검증
```

하지만 이 방식은 문제가 발생했을 때 비용이 크다.

### 불필요한 API 호출이 발생한다

첫 번째 API부터 응답 상태가 이상한데도 나머지 요청을 계속 보내면 호출 한도만 소비하게 된다.

외부 API를 이용하는 배치에서는 호출 횟수도 하나의 자원이다. 특히 여러 API를 조합하는 시스템이라면 이상 상태를 가능한 한 앞에서 발견하는 편이 낫다.

### DB에 중간 데이터가 남을 수 있다

전체 수집 도중 문제가 발견되면 일부 테이블에는 데이터가 들어가고 다른 테이블은 비어 있는 상태가 될 수 있다.

이런 상태에서 이후 요약이나 포스트 생성 로직이 실행되면 실제보다 더 복잡한 문제가 된다.

### 장애 범위를 찾기 어려워진다

인증 문제인지, 지수 API 문제인지, 특정 랭킹 API 문제인지 모르는 상태에서 전체 수집을 실행하면 로그도 길어지고 원인 범위도 넓어진다.

preflight를 통과하지 못했다면 최소한 본 수집 이전의 환경이나 핵심 API부터 확인하면 된다.

## 1. 가장 먼저 API 인증을 확인한다

현재 `preflight_market.py`는 먼저 Kiwoom REST API 토큰을 발급한다.

```text
KiwoomClient 생성
↓
issue_token()
↓
핵심 데이터 조회 시작
```

인증이 되지 않는 상태라면 이후 데이터를 조회할 이유가 없다.

따라서 인증 실패는 전체 수집으로 넘어가기 전에 바로 드러난다.

이 검사는 단순하지만 자동 배치에서는 중요하다. 토큰 발급, 환경변수, API 설정이 잘못된 상태에서 여러 요청을 연속으로 보내는 것을 막을 수 있기 때문이다.

## 2. KOSPI 지수로 거래일과 핵심 값을 먼저 확인한다

인증 다음에는 KOSPI 지수를 조회한다.

현재 지수 조회에는 Kiwoom REST API의 `ka20006`을 사용하고 있다.

수집 함수는 요청 기준일보다 미래인 데이터를 제외한 뒤 가장 최근 거래일을 선택한다. 그리고 해당 거래일의 시가·고가·저가·종가를 숫자로 변환한다.

핵심 OHLC 값이 하나라도 비어 있으면 정상 데이터로 인정하지 않는다.

```text
요청 기준일
↓
지수 응답 목록
↓
기준일 이하의 거래일만 선택
↓
가장 최근 거래일 결정
↓
시가 / 고가 / 저가 / 종가 확인
```

preflight에서는 여기서 얻은 실제 `trade_date`, 종가, 등락률을 로그로 남긴다.

이 과정이 중요한 이유는 **오늘 날짜와 거래일이 항상 같지는 않기 때문**이다.

주말이나 휴장일이 있고, API에 기준일을 전달하더라도 실제 응답에서는 가장 최근 거래일 데이터가 선택될 수 있다.

따라서 자동화에서는 시스템 날짜만 보고 `오늘 데이터`라고 가정하기보다 API가 실제로 반환한 거래일을 명확히 확인해야 한다.

## 3. 거래대금 상위 목록이 비어 있지 않은지 확인한다

지수 하나만 정상이라고 전체 API 상태가 모두 정상이라고 볼 수는 없다.

그래서 preflight에서는 성격이 다른 API를 하나 더 확인한다.

현재 선택한 것은 거래대금 상위 조회 `ka10032`다.

```python
rows = data.get("trde_prica_upper")

if not isinstance(rows, list) or not rows:
    raise RuntimeError("거래대금 상위 응답이 비어 있습니다.")
```

중요한 것은 여기서 상위 종목 전체를 DB에 저장하려는 것이 아니다.

응답이 목록 형태로 존재하고 실제 데이터가 들어 있는지 확인하는 것이 목적이다.

정상이라면 건수와 첫 번째 종목명을 로그로 남긴다.

```text
거래대금 상위 조회 정상: 100건, 첫 종목 ...
```

지수 API와 랭킹 API처럼 서로 다른 성격의 요청을 소량으로 확인하면 인증만 성공한 상태보다 실제 데이터 조회 가능 여부를 조금 더 확실하게 확인할 수 있다.

## 4. API 요청 수도 preflight 결과의 일부다

외부 API를 이용할 때는 데이터뿐 아니라 요청 횟수도 관리해야 한다.

`KiwoomClient`는 현재 실행에서 사용한 요청 수를 누적하고 있고, preflight가 끝나면 다음처럼 사용량을 확인한다.

```text
Office market 사전검증 완료: API 요청 3/20회
```

정확한 허용 횟수는 설정에 따라 달라질 수 있지만 구조적인 의미는 같다.

전체 배치를 시작하기 전에 이미 예상보다 많은 요청을 사용했다면 이후 수집 계획을 다시 확인할 수 있다.

요청 횟수를 로그에 남겨두면 새로운 데이터셋을 추가했을 때 API 비용이 얼마나 늘어나는지도 추적하기 쉽다.

## preflight에서는 일부러 DB에 저장하지 않는다

preflight의 중요한 원칙 중 하나는 **확인용 요청과 실제 저장을 분리하는 것**이다.

KOSPI 지수를 조회하지만 `market_index_daily`에 저장하지 않는다. 거래대금 상위 목록도 응답 상태만 확인하고 실제 랭킹 데이터로 저장하지 않는다.

```text
preflight
API 요청 → 파싱 → 핵심값 확인 → 종료

full batch
API 요청 → 파싱 → DB 저장 → 전체 검증 → 요약 생성
```

이렇게 하면 사전 점검을 여러 번 실행해도 운영 데이터에 영향을 주지 않는다.

개발 중 API 연결 상태만 확인하고 싶을 때도 DB를 초기화하거나 테스트 데이터를 정리할 필요가 없다.

## 동시에 여러 preflight가 실행되는 것도 막았다

실행 스크립트인 `scripts/preflight-market.sh`에는 파일 잠금도 넣었다.

```bash
exec 9>/tmp/office-market.lock
if ! flock -n 9; then
    echo "Office market 수집기가 이미 실행 중입니다."
    exit 3
fi
```

같은 잠금을 사용하는 작업이 이미 실행 중이면 새로운 작업은 바로 종료된다.

처음에는 단순한 테스트 스크립트에 잠금까지 필요한가 싶을 수 있다. 하지만 수동 실행, 예약 실행, 장애 확인 과정이 겹치면 같은 API를 동시에 호출하는 상황이 생길 수 있다.

자동화가 늘어날수록 **중복 실행을 막는 장치도 데이터 검증만큼 중요해진다**.

## preflight 통과가 전체 데이터의 정상까지 보장하지는 않는다

preflight는 빠르게 실패하기 위한 1차 관문이지 최종 검증기가 아니다.

예를 들어 preflight에서 KOSPI와 거래대금 상위 API가 정상이라고 해도 다음 문제는 여전히 남아 있을 수 있다.

- KOSDAQ 거래일이 KOSPI와 다름
- 업종 데이터가 일부만 수집됨
- 시장 폭 종목 수가 지나치게 적음
- 투자자 수급 값이 누락됨
- 금액 단위가 예상과 다름
- 특정 랭킹 종류가 10건 미만으로 저장됨

이런 문제는 실제 데이터를 모두 수집한 뒤에야 확인할 수 있다.

그래서 Office 수집기는 검증을 한 번만 하지 않고 여러 단계로 나눈다.

| 단계 | 목적 | 대표 확인 항목 |
| --- | --- | --- |
| 실행 전 | 중복·시간 조건 확인 | 파일 잠금, 실행 시간 |
| Preflight | 핵심 API 상태 확인 | 인증, KOSPI, 거래대금 상위, 요청 수 |
| 수집 중 | 데이터 기준 통일 | KOSPI/KOSDAQ 거래일 일치 |
| 수집 후 | 전체 정합성 확인 | 건수, 누락, 값 범위, 단위, 랭킹 |
| 게시 전 | 게시 데이터 확인 | 요약 및 Snapshot 생성 가능 여부 |

한 단계의 검증으로 모든 문제를 해결하려 하기보다 각 단계에서 잡기 쉬운 오류를 나눠서 처리하는 방식이다.

## 실제 일일 배치에는 더 강한 안전장치가 있다

`preflight_market.py`와 실제 `daily_batch.py`는 역할이 다르다.

실제 일일 배치는 먼저 실행 시점부터 확인한다.

### 주말에는 실행하지 않는다

토요일과 일요일이면 시장 수집을 건너뛴다.

### 평일 20시 이전에는 최종 수집하지 않는다

Office는 하루가 끝난 뒤 최종 시장 데이터를 만드는 것이 목적이다.

현재 배치는 KRX와 NXT의 애프터마켓까지 고려해 평일 **20:00 이후**에만 최종 일일 데이터를 저장하도록 제한한다.

15시 30분 정규장 종료 직후 데이터를 최종값으로 저장해버리는 상황을 막기 위한 조건이다.

### KOSPI와 KOSDAQ의 거래일이 같아야 한다

배치는 먼저 KOSPI에서 실제 거래일을 정한 뒤 KOSDAQ도 조회한다.

두 시장의 `trade_date`가 다르면 즉시 실패한다.

```text
KOSPI trade_date
        =
KOSDAQ trade_date
```

하루 브리핑 안에 서로 다른 거래일의 지수가 섞이는 것을 막기 위한 조건이다.

### 이미 완료된 거래일은 다시 수집하지 않는다

해당 거래일의 `daily_summary`가 이미 존재하면 기본적으로 `SKIPPED` 처리한다.

예약작업이 중복 실행되거나 같은 날 수동으로 다시 실행해도 불필요한 전체 호출을 반복하지 않기 위한 장치다.

필요할 때만 `--force` 옵션으로 다시 실행할 수 있다.

## 전체 수집 후에는 별도의 정합성 검증을 다시 한다

실제 데이터 저장이 끝나면 `validate_daily_data()`가 수집 결과를 다시 검사한다.

현재 검증 항목에는 다음과 같은 내용이 포함된다.

- KOSPI/KOSDAQ 지수 2건 존재 여부
- 지수 핵심값 누락 여부
- 지수 등락률 비정상 범위 확인
- 시장 폭 데이터 2건 존재 여부
- 상승·보합·하락 종목 수의 음수 및 누락 확인
- 시장 폭 종목 수가 지나치게 적지 않은지 확인
- 업종 데이터 최소 건수 확인
- 업종 수급 데이터 최소 건수와 금액 단위 확인
- 시장 전체 투자자 수급 값과 단위 확인
- 각 랭킹 데이터의 건수, 단위, 대상 universe 확인
- 전체 API 요청 수가 설정 한도를 넘지 않았는지 확인

즉 구조는 다음과 같다.

```text
preflight
↓
전체 수집
↓
DB 저장
↓
validate_daily_data
↓
daily_summary 생성
↓
Snapshot 공개
↓
브리핑 생성 단계
```

잘못된 데이터가 발견되면 요약과 게시 단계로 넘어가지 않는 것이 핵심이다.

## 실패 기록도 운영 데이터다

실제 배치 실행은 `collection_run`에 실행 상태를 기록한다.

정상 완료하면 `SUCCESS`, 이미 완료된 거래일이면 `SKIPPED`, 오류가 발생하면 `FAILED` 상태로 남긴다.

함께 저장하는 정보는 다음과 같다.

- 시작 시각
- 종료 시각
- 요청 기준일
- 실제 거래일
- API 요청 수
- 상태
- 실패 메시지

자동화에서는 성공 데이터만 남기는 것보다 **왜 실행되지 않았는지 추적할 수 있는 정보**도 중요하다.

예약 실행이 실패했을 때 단순히 "오늘 글이 없다"가 아니라 어느 단계에서 중단됐는지 확인할 수 있어야 한다.

## preflight를 사용하면서 기준이 명확해졌다

현재 수동으로 사전 검증할 때는 다음 스크립트 하나를 실행한다.

```bash
bash scripts/preflight-market.sh
```

정상적인 경우 확인하고 싶은 로그는 복잡하지 않다.

```text
KOSPI 조회 정상
거래대금 상위 조회 정상
Office market 사전검증 완료
```

여기서 문제가 생기면 전체 배치로 넘어가지 않고 먼저 API 인증, 반환 거래일, 응답 형식, 요청 수를 확인한다.

반대로 preflight가 정상이라면 핵심 API 연결은 통과했다고 보고 전체 수집 단계로 넘어간다.

이 작은 단계를 추가한 뒤 운영 기준도 단순해졌다.

```text
핵심 API가 정상인지 모름
→ 전체 수집부터 실행
```

이 아니라

```text
preflight 실패
→ 원인 확인

preflight 성공
→ 전체 수집
→ 전체 정합성 검증
→ 게시
```

처럼 단계가 명확해졌다.

## 핵심은 실패를 가능한 한 앞에서 발견하는 것이다

데이터 수집 시스템에서 검증은 마지막에 한 번 실행하는 부가 기능이 아니다.

문제를 발견할 수 있는 가장 이른 지점에서 멈추도록 여러 방어선을 두는 것이 더 안전하다.

Office에서는 현재 다음 원칙으로 정리하고 있다.

1. 실행 전에는 중복 실행과 시간 조건을 확인한다.
2. 전체 수집 전에는 최소 API 호출로 핵심 상태를 확인한다.
3. 수집 중에는 거래일과 데이터 기준을 통일한다.
4. 수집 후에는 DB에 저장된 결과를 다시 검증한다.
5. 검증을 통과한 데이터만 요약과 게시 단계로 보낸다.

결국 preflight의 역할은 데이터를 많이 검사하는 것이 아니다.

**잘못된 상태에서 큰 작업을 시작하지 않게 만드는 것**이다.

## 다음 단계

preflight를 통과했다고 해서 데이터 수집이 끝난 것은 아니다.

실제로 더 많은 오류는 여러 API의 결과를 DB에 저장한 뒤 서로 비교할 때 발견된다. 단순히 데이터가 존재하는지뿐 아니라 건수, 값의 범위, 단위, 시장 구분까지 확인해야 한다.
