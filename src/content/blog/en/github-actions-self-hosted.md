# Deploy to a Private Server with GitHub Actions Self-hosted Runner

A server-side `git pull` deployment is simple, but the server itself has to decide when to check for changes.

A push-driven workflow can instead start deployment when code reaches the `main` branch. This makes it easier to connect a specific source revision to a specific deployment.

The challenge appears when the target machine is behind a router or firewall. If a GitHub-hosted Runner cannot SSH directly into that private server, a **Self-hosted Runner inside the private network** can execute the deployment job instead.

## Limitations of server-side pull deployment

A pull-based deployment usually looks like this:

```text
Developer → GitHub
               ↑
          Server pulls
```

With a manual `git pull`, someone must connect to the server for every deployment. A cron-based approach removes the manual step, but the server still polls the repository on a schedule.

A CI/CD pipeline can use the repository event itself as the deployment trigger.

## Why a private server changes the design

SSH deployment from a GitHub-hosted Runner requires the target server to be reachable from that Runner.

A server that only has a private address is not directly reachable this way.

```text
GitHub-hosted Runner
        X
        ↓
192.168.x.x private server
```

Instead of exposing the server for inbound deployment traffic, a Self-hosted Runner can run on the deployment server or another appropriate machine inside the same network.

## Self-hosted Runner architecture

A Self-hosted Runner is a machine that executes GitHub Actions jobs.

```text
main push
   ↓
GitHub Actions
   ↓
Self-hosted Runner
   ↓
build / deploy inside private network
```

The important distinction is that GitHub does not need to open an SSH connection directly to the private server. The Runner communicates with GitHub Actions and receives jobs to execute.

This avoids exposing an SSH port to the internet solely for deployment.

## Register the Runner

Open the Actions Runner settings for the repository and follow the current installation instructions for the server operating system.

A typical Linux setup follows this pattern:

```bash
mkdir actions-runner
cd actions-runner

# Download and extract the Runner package using GitHub's current instructions
# Run the registration command shown in repository settings

./config.sh --url https://github.com/username/project --token <registration-token>
```

Do not commit or publish the registration token. Use the current command generated by GitHub's settings page.

Start the Runner with:

```bash
./run.sh
```

For a long-running deployment server, configure the Runner as a service so it does not depend on an interactive terminal session.

## Create the workflow

Create `.github/workflows/deploy.yml` and trigger it on pushes to `main`.

```yaml
name: Deploy

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: self-hosted

    steps:
      - uses: actions/checkout@v4

      - name: Deploy
        run: ./deploy.sh
```

The key difference is `runs-on: self-hosted`.

When a commit reaches `main`, the registered Runner receives the job and executes `deploy.sh`.

## Do you still need git pull on the server?

`actions/checkout` checks out the workflow commit into the Runner workspace.

That means a separate production directory that repeatedly runs `git pull` is not required for every deployment design.

A build-artifact deployment can instead follow this flow:

```text
GitHub main
   ↓
actions/checkout
   ↓
build
   ↓
Docker image or deployment artifact
   ↓
restart service
```

Separating the source checkout from the runtime directory can make the deployment process easier to reason about.

## Docker deployment example

For a service managed by Docker Compose, `deploy.sh` might contain:

```bash
#!/bin/bash
set -e

docker compose build
docker compose up -d
```

A real project can add tests, environment validation, image cleanup, and other required steps.

Do not put `.env` values, API keys, passwords, or other secrets directly in the workflow file.

## Minimize Runner permissions

A Self-hosted Runner executes real commands on its host.

The Runner account should therefore receive only the permissions required for deployment rather than unrestricted root access.

If Docker access is required, grant only the access necessary for the deployment design and keep unrelated directories and services outside the Runner's scope.

Self-hosted Runners also require extra caution in repositories where untrusted contributors can modify or trigger workflows.

## Separate validation from deployment

Not every push to `main` has to become an unconditional deployment.

The workflow can separate validation and deployment:

```text
push
 ↓
test
 ↓
build
 ↓
deploy
```

The deploy job can depend on successful tests and builds, preventing a failed validation stage from continuing into deployment.

## Summary

When replacing server-side `git pull` with GitHub Actions, network reachability should be considered before choosing the deployment mechanism.

For a server that is not directly reachable from the public internet, a Self-hosted Runner provides a practical event-driven deployment model.

```text
Before
server → check GitHub → git pull

After
GitHub push → Actions job → private Runner executes deployment
```

This architecture can connect a `main` push to automated build and deployment without exposing the private server's SSH port solely for CI/CD.
